# v1.3.0-alpha.1: explicit HTTP identity transport

Date: 2026-10-17 (Asia/Seoul). Python package `1.3.0a1`, CMake/native project
`1.3.0`, runtime ABI v1, FDAR v1, semantic RPC schema v1, store base schema v2.
Baseline: `v1.2.0-rc.2` (`5b131f2b7617b67087dc8a7876f1b9486cf90688`), based on
the supplied improvement PDF's implementation commit `cb02d7a` (PR #6).

## Problem and result

The shopping fixture previously transported only low64 trace IDs and passed
absolute monotonic deadlines between peers. It also logged every process as
generation1. This alpha preserves both trace halves over version00 W3C
traceparent, keeps client/server span identities separate from the explicitly
shared numeric RPC identity, records the real process generation and optional
local clock provenance, and starts receiver deadlines from relative budgets.
Absent/ambiguous context and unknown clocks do not become positive evidence.

The [HTTP contract](../http-context.md) defines APIs, validation, legacy inbound
compatibility and the fixture mapping. The standalone adapter is reusable in
other Python HTTP applications without a provider registry or tracing SDK.

## Scope and compatibility

- Version00 traceparent only; unsupported versions, duplicate/invalid fields and
  conflicting legacy traces fail explicitly. `tracestate` is outside this API.
- Flags00 propagate normally. Raw parsed flags remain available as input evidence;
  outgoing v00 headers clear reserved bits and preserve only the sampled bit.
  Sampling hints do not prove observations.
- Existing low64 application input remains valid with optional high64 default0.
- Native RPC records retain high/low trace fields. W3C spans stay application
  evidence; no new native span ABI or general retry/attempt pairing is claimed.
- Legacy low64 shop ingress is supported. New outbound W3C peers require this
  adapter; mixed-version outbound negotiation is not implemented.
- Relative budgets1..5000ms start on receipt. Legacy absolute deadlines are
  ignored and labeled. Transit time and end-to-end deadlines are not measured.
- Clock metadata requires Linux boot UUID plus time namespace; missing sources
  stay unknown. Namespace lifetime is not persistently verified. Clock fields
  are optional self-reported provenance, not synchronization or authentication.
- `process_generation` now rejects bool, float and noncanonical decimal strings;
  canonical environment decimal strings are normalized to an integer.
- Existing required CLI/MCP tools, ABI/FDAR/store formats stay compatible.

## What remains open

This implements the first bounded part of PDF stage F, and partly covers v1.3
P1-01/P1-02. General retry mapping, native clock metadata, container/Pod UID
lifecycle and cross-process native HTTP topology acceptance remain open.
Stage G's fault proxy/durable retry oracle, H's 8/16/32 scale and measured retained
snapshots, I's general viewer/drill-down, and J's full release program stay open.

NOT RUN for this milestone: final current-revision provenance-enabled core/gRPC
release profiles, Docker N=8/16/32, kind, 1800-second soak, external libuv corpus
rerun and independent final stable audit. Existing CTest/gRPC scenarios and
Clang18 smoke do not replace those profiles. Stable v1.2/v1.3 remains NO-GO.

## Adoption and contribution sequence

REA's history favors exact version/data contracts, source-backed evidence,
shared CLI/MCP meaning and installed-path acceptance (supplied REA PDF pp.9-13,
20-25,46-49,54). This milestone follows that sequence while avoiding a new
workflow DSL or speculative provider framework. REA's popularity/impact is not
an outcome we can establish from this change.

1. Keep one newcomer path: install the tagged source/package, run doctor,
   capture a C/C++ fixture, inspect its CLI/MCP summary and source/unknowns.
2. Next accept an outside project's reproducible failing fixture; preserve
   exact binary/build/trace identity and a negative oracle with each fix.
3. Complete the stageG durable retry/fault/recovery oracle before scaling
   apparent topology or claiming operational retry safety.
4. Measure task completion, failure diagnosis, input/output cost and loss on
   fixed workloads; publish numbers and limitations before adding cache/UI.
5. Close full release gates and independent audit before a stable version.
